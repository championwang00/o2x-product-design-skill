## 如何使用

1. **同时读两层**：通用规范与已发布 One2X 库提供共享 token、组件身份和通用行为；模块上下文提供该模块的布局、密度、角色、状态关系与默认方案。目标项目提供组件 API、token 名称映射、路由和状态管理约定。模块特例保留来源和范围，不静默改全局规范。用户当前明确要求决定本次范围与授权；会改变结果且无法从现有证据裁决的冲突才询问。
2. **读取当前参考**：开始相关 UI 工作时，通过 Figma MCP 读取对应参考的当前结构、相关 UI 截图和相邻状态；大 section 先定位子节点，token 敏感部分另查变量/文字样式。新 UI 从同模块同角色组件延伸，核对字阶、间距、图标、对齐、密度和状态表达，不凭通用模板重新发明。
3. **辨认确认状态**：默认、并列状态、备用、待确认分别处理。参考画面里的注释/连线/外框是说明，不是产品 UI；日期较新或图画得完整不代表已经批准。未确认的方案不自动进入默认流程。
4. **保留简短证据**：任务记录中写出已读的通用章节、模块文件与参考节点、采用的方案，以及新增 UI 如何复用现有组件/token；说明冲突、设计指定例外与未核验项。交付时对照同模块参考检查，而非仅检查 token 名称。

没有登记的模块：先查目标项目已有实现和用户指定设计，按通用规范推进能确定的部分；只有关键基线缺失才提问。不能借用不相干模块的尺寸来假定其标准。确认了可复用模块上下文后，再按下节登记。

参考无法访问：使用此处已记录的文字基线和可用项目证据，明确哪些外观/状态无法核验，继续不依赖缺失证据的工作；不得声称已完全对稿。

## 收到模块上下文时自动迭代与同步

当用户明确把设计稿、文档或反馈作为某模块的新增/修订上下文时，同一任务内执行以下流程，不等用户再次提醒“更新索引”或“同步”。这是本工作流的既定范围；用户本次明确限制（如仅分析、先审后改、不发布）优先。普通参考链接、只读比较或未选定的探索不自动变成模块基线。

1. **读来源并识别模块**：核对来源内容、模块范围与确认状态，先查索引里的名称和别名，避免同模块重复建档。Figma 记录 fileKey/node；不能访问的部分标明未核验，不编造摘要。只有模块归属或替换关系会实质改变结果、且现有上下文无法判断时才询问。
2. **合并更新**：已登记模块修改原文件；新模块建立 `modules/<module>.md` 并补索引的名称、匹配词和入口。记录适用范围、来源、已确认规则、默认/备用/待确认、通用规范关联和核对日期。新增内容融入已有章节，保留仍有效的上下文；旧来源被明确替换时说明替代关系。模块特例不提升为通用标准；实际可跨模块复用且有依据的规则才更新 `design.md` 与相应执行入口。
3. **验证并同步**：核对索引到正文、正文到来源与通用规范的链接；检查重复/冲突和未确认状态，验证改动 skill 的 frontmatter、受影响入口与安装路径。记录本次增量到 `CHANGELOG.md`，再完成下表各处的同步。
4. **报告实际状态**：简短列出更新的模块和各处同步结果，附公开提交或项目 PR。区分“本机已生效”“公开分支已发布”“项目指针已跟随”“PR 待合并”“已合并”；指针能读取新内容不代表某个 PR 已合并。遇到权限、网络、检查或分支保护阻塞，保留可审阅的改动并明确未完成项，不报告全部同步成功。

## 维护与分发

每个模块文件保留：适用范围、权威参考（fileKey/node）、默认/备用/待确认、相关通用章节、最后核对日期。只添加有实际用途的模块；索引写匹配入口，模块正文只维护一处，其他 skill 使用链接。

Figma 变化需要核对确认状态后再更新文字基线；链接、摘要和核对日期一起维护，不能将画布中新增内容自动视为已批准。模块参考链接不等于对该文件的修改授权。One2X 库来源、模块参考与本次授权写入目标分别记录。

本目录与 `design.md`、`tokens/` 一起分发。全局软链接继续指向同一规范库；消费项目保留指针入口，同时解析通用规范与本目录，不复制产品规则形成第二份来源。
