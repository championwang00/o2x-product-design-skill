# O2X Polish Distill

一次走查里，设计师会连续给几十条「选中元素 + 截图 + 一句话」的调整。结束后要把能复用的部分写进 One2X 规范，下次就不用再被指出同样的问题；设计师的走查习惯也要写进 `o2x-design-system`，让之后的配合更顺。

产出三样东西：规范仓库的一次提交；各 skill 库入口都指向这份规范；一份中文汇报。

## 位置与边界

- **规范唯一来源**：解析本文件的真实路径（它通常是软链接），往上三级是规范仓库根目录（本机为 `~/Desktop/O2X Product Design skill`，远端 `championwang00/o2x-product-design-skill`）。
- **写到哪里**：
  - 规则正文：仓库根 `design.md`；
  - 执行要点、检查项、走查协作方式：`.cursor/skills/o2x-design-system/SKILL.md`；
  - 动效细节：仓库内 `web-animation-design`，或者在 `design.md` 里交叉引用它；
  - 路由：新增 skill 或新任务类型时，登记到 `o2x-product-design`。
- **只写前端**：布局、间距、圆角、颜色 token、字体、组件状态、交互流程、动效、空状态、骨架。以下内容不写：
  - 后端、接口、数据含义（例：标签「-」是不是后端给的）；
  - i18n 同步流程、埋点；
  - 部署、登录、Git 操作。
- **不要碰仓库里别人的未提交改动**：只 `git add` 本次改的文件。

## 流程

### 1. 收集原话

会话长了会被压缩，只凭当前上下文会漏掉前半段。先把原话全部取出来：

```bash
python3 scripts/extract_user_messages.py --latest ~/.claude/projects/<编码后的项目路径>
# 或指定文件：python3 scripts/extract_user_messages.py <session-id>.jsonl
```

脚本能抓到三类消息：普通消息、工作中途排队插入的消息、带截图插入的消息。选中元素的 HTML 会折叠成 `[选中元素]`。配合会话摘要、本次提交（`git log --stat`）和代码现状一起看。

### 2. 以最终状态为准

- 同一处来回改过的，只记最后定下的值。例如勾选框填充先后试过 Background 90、Scrim 40，最后又改回 Background 90，那么中间方案不进规范。
- 数值从代码或浏览器计算值核对，不凭记忆写。token 的名字不等于计算值，比如 Medeo 的 `--Radius-8` 实际是 10px。规范里写实际生效的数，并注明来源 token。

### 3. 逐条分类

分类方法沿用 `design-feedback-judge`（如已安装），这里是适配走查场景的版本：

| 类别 | 怎么判断 | 去向 |
| --- | --- | --- |
| 通用规则 | 换一个页面也成立（例：勾选框全页一套样式；多选中的条目只靠勾选框表达） | `design.md` 对应章节正文，加 Medeo 实例 |
| 产品参考值 | 某个页面定下的具体数值（例：命令框收起态 427×44） | `design.md` 参考值表（如 §7.6） |
| 已有规则没被执行 | 规范早写过，这次没做到（例：Geist Mono 用 `ss09` 去斜杠 0） | 不重复写规则。查清为什么没被读到（入口没链到某个工具、规则放错章节、描述不够好搜），修入口或改写规则 |
| 推翻旧规则 | 和现有正文冲突（例：菜单圆角从 `--Radius-8` 改成字面 6px） | 改原文，不让新旧说法并存；参考值表同步 |
| 一次性偏好 | 只针对这一处，也没给理由 | 不写，在汇报里列出 |
| 走查习惯 | 设计师做事的方式，重复出现两次以上或明确说过 | `o2x-design-system`「走查协作方式」 |

判断「通用」时，问一句：这条规则换到别的页面，设计师会不会再说一遍？会，就写成规则；只在这个页面成立，就进参考值表。

### 4. 先读现有正文，再改

- 通读 `o2x-design-system` 全文和 `design.md` 的相关章节，grep 这次涉及的旧数值（圆角、间距、颜色 token 名）。
- **改而不是追加**：
  - 收紧模糊的规则；
  - 改掉被推翻的表述和参考值；
  - 补上缺失的交叉引用；
  - 把放错位置的内容移回该在的章节。
- **新检查同步到三处**：`design.md` §11 Do / Don't、§13.3 Iteration checklist、`o2x-design-system`「完成验收」。
- **写法**：
  - 中文，短句；
  - 写「怎么做 + 为什么」，并附 Medeo 实例；
  - 不写成一次性指令（「把 X 改成 Y」）；
  - 执行要点只留一句话并指向 `design.md` 章节，长规格和数值表放进 `design.md`。

### 5. 记录

- `CHANGELOG.md`「Unreleased」下加一条，写明来源（哪个页面、哪次走查）；
- `design.md` 附录 B 修订记录加一行。

### 6. 同步到各 skill 库

```bash
bash scripts/link_global_skills.sh        # 检查
bash scripts/link_global_skills.sh --fix  # 补上缺失的链接
```

- 各工具的全局入口（`~/.claude/skills`、`~/.codex/skills`、`~/.cursor/skills`、`~/.agents/skills`）都应是指向规范仓库的软链接，不维护副本。只要链接在，改仓库就等于同步，不需要再拷贝。
- 已存在的独立目录，脚本只报告、不覆盖。请用户确认后移出技能目录备份，再改成链接。
- **项目仓库里的副本**（如 medeo-fe `.agents/skills/one2x-design-system`）是独立快照，受该项目的提交流程约束。不要在这里静默修改：汇报它和规范的差异，征得同意后按那个项目的规则（分支、PR）处理。
- **推送规范仓库**：用户要求「同步」即视为同意推送规范仓库本身。提交信息参照 `git log` 的风格（`docs: …`，英文），结尾加协作署名。其他仓库的推送另外确认。

### 7. 验证

- grep 被推翻的旧数值和旧说法，确认已经清掉；
- 检查新写的 `§x.y` 引用都存在，相对路径能解析；
- 重新运行 `link_global_skills.sh`，所有入口都显示 `ok`；
- 新 skill 的 frontmatter 有 `name` 和 `description`。

### 8. 汇报（中文）

按以下结构：

1. **写进规范的**：表格列出「调整 → 类别 → 写到哪里（文件与章节）」；
2. **修正的旧说法**：被推翻、改掉的原文；
3. **没写进去的**：后端相关、一次性偏好、中间方案，各附一句原因；
4. **需要设计确认的**：规则之间的冲突、跨页面不一致（如两处工具栏圆角一个是变量一个是字面值）；
5. **同步状态**：提交链接；各 skill 库入口检查结果；项目副本的处理建议。
